# Анализ идемпотентности процессинга документов

## Обзор

Процессинг документов **частично идемпотентный**. Разные компоненты ведут себя по-разному при повторной обработке.

## Компоненты и их идемпотентность

### 1. DocumentProcessor (Обработка документа)

**Статус:** ❌ **НЕ идемпотентный** (но безопасный)

**Поведение:**
- Документ всегда обновляется через `Upsert`
- Статус меняется: `"embedded"` → `"processing"` → `"processed"`
- Данные перезаписываются:
  - `Categories` - полностью заменяются
  - `Attrs` (sentiment, keyPoints, topics, outlinks) - полностью заменяются
  - `Language` - перезаписывается
  - `DocumentType` - перезаписывается
  - `Attrs["summary"]` - перезаписывается

**Последствия повторного запуска:**
- Документ будет обработан заново
- LLM извлечение выполнится снова (расход токенов)
- Данные могут измениться, если LLM вернет другие результаты
- Статус всегда будет `"processed"` в конце

**Рекомендация:** Безопасно запускать повторно, но будет расход токенов.

---

### 2. Entities (Сущности)

**Статус:** ✅ **Идемпотентный**

**Поведение:**
- Использует `EntityResolver.ResolveEntity()` для проверки существующих entities
- Если entity с таким `canonicalName` и `type` уже существует → использует существующий ID
- Если не существует → создает новый

**Код:**
```go
existing, err := e.entityResolver.ResolveEntity(ctx, tenantID, canonicalName, entityType)
if err == nil && existing != nil {
    entityIDs[canonicalName] = existing.ID
    continue  // Используем существующий, не создаем дубликат
}
// Создаем новый только если не найден
```

**Последствия повторного запуска:**
- Существующие entities не дублируются
- Новые entities создаются только если их еще нет
- Идемпотентный ✅

---

### 3. Events (События)

**Статус:** ❌ **НЕ идемпотентный**

**Поведение:**
- Всегда создает новый Event через `eventsRepo.Create()`
- НЕ проверяет существующие события
- Каждый раз создается новый Event с новым ID

**Код:**
```go
event := &models.Event{...}
eventID, err := e.eventsRepo.Create(ctx, event)  // Всегда создает новый
```

**Последствия повторного запуска:**
- Создаются дубликаты событий
- Одно и то же событие может быть создано несколько раз
- НЕ идемпотентный ❌

**Пример:**
- Первый запуск: создается Event "Запуск проекта X" (ID: abc123)
- Второй запуск: создается Event "Запуск проекта X" (ID: def456) - дубликат

---

### 4. Claims (Утверждения)

**Статус:** ❌ **НЕ идемпотентный**

**Поведение:**
- Всегда создает новый Claim через `claimsRepo.Create()`
- НЕ проверяет существующие claims
- Каждый раз создается новый Claim с новым ID

**Код:**
```go
claim := &models.Claim{...}
claimID, err := e.claimsRepo.Create(ctx, claim)  // Всегда создает новый
```

**Последствия повторного запуска:**
- Создаются дубликаты claims
- Одно и то же утверждение может быть создано несколько раз
- НЕ идемпотентный ❌

**Пример:**
- Первый запуск: создается Claim "Компания X выпустила продукт Y" (ID: xyz789)
- Второй запуск: создается Claim "Компания X выпустила продукт Y" (ID: mno012) - дубликат

---

## Итоговая оценка

| Компонент | Идемпотентность | Последствия повторного запуска |
|-----------|----------------|-------------------------------|
| DocumentProcessor | ❌ Нет | Перезапись данных, расход токенов LLM |
| Entities | ✅ Да | Используются существующие, дубликатов нет |
| Events | ❌ Нет | Создаются дубликаты событий |
| Claims | ❌ Нет | Создаются дубликаты утверждений |

## Рекомендации

### Текущее состояние
- **Entities** - безопасно запускать повторно (идемпотентны)
- **Events и Claims** - создают дубликаты при повторном запуске

### Что можно улучшить

1. **Добавить проверку для Events:**
   - Проверять существующие события по `Title` + `OccurredAt` + `tenantID`
   - Использовать существующий Event, если найден

2. **Добавить проверку для Claims:**
   - Проверять существующие claims по `SubjectRef` + `Predicate` + `ObjectRef.Value` + `tenantID`
   - Использовать существующий Claim, если найден

3. **Добавить проверку статуса документа:**
   - Пропускать обработку, если документ уже имеет статус `"processed"`
   - Или добавить флаг `forceReprocess` для принудительной обработки

---

## Пример поведения при повторном запуске

**Сценарий:** Запуск репроцессинга для документа, который уже был обработан

1. **DocumentProcessor:**
   - Статус: `"processed"` → `"processing"` → `"processed"`
   - Данные перезаписываются (Categories, Attrs, Language)
   - LLM извлечение выполняется заново

2. **Entities:**
   - "Nvidia" уже существует → используется существующий ID
   - "OpenAI" уже существует → используется существующий ID
   - "NewCompany" не существует → создается новый

3. **Events:**
   - "Запуск проекта" → создается новый Event (дубликат)
   - "Релиз версии 1.0" → создается новый Event (дубликат)

4. **Claims:**
   - "Компания X выпустила продукт Y" → создается новый Claim (дубликат)
   - "Проект завершен" → создается новый Claim (дубликат)

**Результат:** Документ обработан, но созданы дубликаты Events и Claims.
