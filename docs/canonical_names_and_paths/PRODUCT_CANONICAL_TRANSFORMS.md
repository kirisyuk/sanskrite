# Product Canonical Transforms

## Что это за слой

Это слой эталонных продуктовых переделов.

Его задача:
- хранить пары вида `из -> в`
- описывать реальные канонические шаги переработки, производства или сборки
- позволять потом собирать длинные продуктовые цепочки из коротких эталонных шагов

Примеры смысла:
- `bauxite -> alumina`
- `spodumene concentrate -> lithium carbonate`
- `lithium hydroxide -> pCAM`
- `pCAM -> cathode active material`
- `battery cell -> battery module`
- `battery module -> battery pack`

Важно:
- это не синонимы
- это не просто соседство в поставке
- это не широкая ассоциация “используется где-то рядом”
- это именно канонический шаг преобразования одного продукта в другой

## Как пары собирались

Пары переделов собирались из реальных данных графа по трём типам сигналов:

1. Прямые продуктовые связи `TRANSFORMS_INTO`
2. Реальный вход-выход у одного и того же производителя или площадки
3. Уже материализованные assembly/transform связи в собранных supply-chain артефактах

Перед началом поиска продукты сначала были приведены к каноническим синонимам.
Это означает, что переделы строятся уже не между alias-хвостами, а между относительно устойчивыми продуктами.

## Какие пары считались хорошими

В словарь попадали только пары, где:
- из одного продукта действительно получается другой
- переход выглядит как реальный шаг переработки, refining, manufacturing или assembly
- шаг достаточно локальный и канонический

Сюда же относятся прямые assembly-переходы вида:
- `готовый модуль -> конечный продукт`
- `готовый узел -> конечное устройство`
- `готовый pack/module -> конечное изделие`

Если между ними нет полезной отдельной продуктовой стадии в данных, такой переход считается допустимым.

Пример допустимого смысла:
- `Kunlun Glass Display Module -> Huawei Mate 60 Pro`

Почему это допустимо:
- модуль не является просто абстрактной категорией
- конечный продукт тоже конкретный
- между ними нет обязательной отдельной канонической продуктовой стадии, которую нужно вставить в цепь
- для сборки длинных materialized chains дырка хуже, чем такой прямой очевидный assembly step

Особенно важно:
- брались не длинные прыжки через несколько очевидных стадий
- брались именно шаговые переходы, из которых потом можно собрать длинную цепь

То есть правило такое:
- если переход прямой и ближайший, его можно брать даже до конечного finished product
- если переход перескакивает через несколько очевидных промежуточных продуктов, его брать нельзя

Пример правильной логики:
- хорошо: `battery cell -> battery module`
- хорошо: `battery module -> battery pack`
- плохо: `battery cell -> electric vehicle`

## Какие пары отбрасывались

Из словаря специально выбрасывались:
- синонимы одного и того же продукта
- классы и подклассы
- слишком широкие и абстрактные категории
- сервисы и логистика
- комплаенс, документы, маршруты, операции
- генерация энергии как конечный output
- длинные прыжки через пропущенные промежуточные стадии

Но не отбрасывались прямые final-assembly кейсы, если они ближайшие по смыслу.

## Насколько это уже полезно

Результат уже даёт не только отдельные пары, но и длинные осмысленные цепочки.

Пример уже наблюдаемой длинной цепи:
- `lithium ore`
- `spodumene concentrate`
- `lithium carbonate`
- `lithium hydroxide`
- `pCAM`
- `cathode active material`
- `battery electrode`
- `EV battery cell`
- `EV battery module`
- `EV battery pack`

То есть словарь уже позволяет собирать цепочки существенно длиннее 2-3 шагов.

Сильнее всего сейчас проявлены домены:
- battery materials and battery manufacturing
- semiconductors
- uranium / nuclear fuel cycle
- oil refining
- steel

## Как это использовать другому агенту

Другой агент должен считать, что:

1. Базовая единица здесь — не имя, а канонический продуктовый путь.

2. Пара `A -> B` означает:
- `A` является допустимым каноническим upstream input
- `B` является допустимым downstream result

3. Из этих пар можно строить длинные цепочки, проходя по графу шаг за шагом.

4. Если один продукт ведёт в несколько downstream продуктов, это нормально.
Производство ветвится.

5. Если один downstream продукт собирается из нескольких upstream компонентов, это тоже нормально.
Этот словарь не запрещает многовходовые сборки.

6. Прямая сборка в finished product тоже допустима.
Если в данных есть непосредственный ближайший переход `module/component -> final device/model`, его можно использовать как валидный шаг цепочки.

## Ограничение текущего результата

Работа не исчерпала всю базу полностью.

Уже обработаны первые `1200` наиболее сильных кандидатов, и из них выделен безопасный эталонный слой.
Следующий диапазон `1200..1499` уже снят как raw/curated continuation point, но ещё не записан в Firestore, потому что там остаётся заметный long tail широких и process-like кейсов.

Но уже сейчас результат достаточно осмысленный, чтобы использовать его как опорный слой для сборки material/product chains.

## Отдельная архитектурная заметка

Сейчас этот словарь хранит вместе:
- переработку/конверсию материалов
- manufacturing steps
- assembly steps

С бизнес-точки зрения это допустимо, пока шаг остаётся ближайшим и каноническим.

Но в будущем имеет смысл рассмотреть отдельный тип отношения, например:
- `ASSEMBLED_INTO`

Зачем это может понадобиться:
- чтобы отделить химический/технологический передел от сборочного шага
- чтобы при желании строить разные виды цепочек
- чтобы downstream-алгоритмы могли различать conversion и assembly

Пока такого типа нет, прямые assembly steps допустимо хранить в текущем canonical transform dictionary.
