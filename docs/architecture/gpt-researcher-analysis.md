# GPT Researcher - Анализ архитектуры и принципов работы

## Обзор

**GPT Researcher** — это агент для глубокого исследования, который проводит автоматизированное исследование по заданной теме и генерирует подробные отчеты с цитатами. Система использует подход "планировщик-исполнитель" для параллельной обработки информации из множества источников.

## Основная архитектура

### Концепция: Planner-Executor-Publisher

Система построена на трех основных компонентах:

1. **Planner (Планировщик)** — генерирует исследовательские вопросы
2. **Executor (Исполнитель)** — собирает информацию по каждому вопросу
3. **Publisher (Публикатор)** — агрегирует все находки в финальный отчет

### Архитектурная диаграмма процесса

```
Запрос пользователя
    ↓
Выбор агента и роли (LLM)
    ↓
Планирование исследования (генерация под-вопросов)
    ↓
Параллельный сбор информации:
    ├─ Web Search (Tavily, Bing, Google, DuckDuckGo, etc.)
    ├─ MCP Retrievers (специализированные источники)
    ├─ Local Documents (PDF, DOCX, TXT, etc.)
    └─ Vector Store (семантический поиск)
    ↓
Скрапинг найденных URL
    ↓
Извлечение и сжатие контекста
    ↓
Курация источников (фильтрация и ранжирование)
    ↓
Генерация отчета (LLM)
    ↓
Финальный отчет с цитатами
```

## Ключевые компоненты

### 1. GPTResearcher (agent.py)

**Главный класс-оркестратор** всей системы.

**Основные методы:**
- `conduct_research()` — проводит исследование
- `write_report()` — генерирует финальный отчет
- `quick_search()` — быстрый поиск по запросу

**Инициализация:**
- Принимает query, report_type, report_source, tone и другие параметры
- Настраивает retrievers (поисковые системы)
- Инициализирует компоненты: ResearchConductor, ReportGenerator, ContextManager, BrowserManager, SourceCurator

### 2. ResearchConductor (skills/researcher.py)

**Управляет процессом исследования.**

**Основной поток:**

1. **Планирование исследования** (`plan_research()`):
   - Выполняет начальный поиск по запросу
   - Генерирует под-вопросы для глубокого исследования
   - Использует LLM для создания стратегии исследования

2. **Проведение исследования** (`conduct_research()`):
   - Выбирает источник данных (Web/Local/Hybrid/Azure/VectorStore)
   - Параллельно обрабатывает под-вопросы (`asyncio.gather`)
   - Для каждого под-вопроса:
     - Ищет релевантные URL через retrievers
     - Скрапит контент с найденных страниц
     - Извлекает релевантный контекст через семантический поиск

3. **Обработка под-вопросов** (`_process_sub_query()`):
   - Поддержка MCP стратегий:
     - **fast**: MCP запускается один раз для основного запроса, результаты кешируются
     - **deep**: MCP запускается для каждого под-вопроса
     - **disabled**: MCP отключен
   - Комбинирует результаты MCP и веб-поиска

### 3. ReportGenerator (skills/writer.py)

**Генерирует финальные отчеты на основе собранного контекста.**

**Функции:**
- `write_report()` — основной метод генерации отчета
- `write_introduction()` — генерация введения
- `write_report_conclusion()` — генерация заключения
- `get_subtopics()` — извлечение подтем
- `get_draft_section_titles()` — генерация заголовков разделов

**Процесс генерации:**
1. Получает собранный контекст
2. Использует LLM для генерации структурированного отчета
3. Поддерживает различные форматы: markdown, PDF, DOCX
4. Добавляет цитаты к источникам

### 4. Retrievers (retrievers/)

**Множество поисковых систем для получения URL.**

**Поддерживаемые retrievers:**
- **Tavily** — специализированный поиск для AI
- **Bing** — Microsoft Bing Search
- **Google** — Google Search API
- **DuckDuckGo** — бесплатный поиск
- **SerpAPI** — универсальный API поиска
- **Serper** — Google Search API
- **Exa** — семантический поиск
- **ArXiv** — научные статьи
- **PubMed Central** — медицинские публикации
- **Semantic Scholar** — академический поиск
- **MCP Retriever** — интеграция с Model Context Protocol серверами
- **Custom** — пользовательские retrievers

**Как работают:**
- Каждый retriever принимает query и возвращает список результатов с URL, заголовками и сниппетами
- Система может использовать несколько retrievers параллельно
- MCP retrievers используют двухэтапный подход: выбор инструментов → выполнение поиска

### 5. Scraper (scraper/)

**Извлекает контент с веб-страниц.**

**Типы скраперов:**
- **BrowserScraper** — использует браузер (Playwright/Nodriver) для JavaScript-сайтов
- **BeautifulSoupScraper** — быстрый парсинг HTML
- **TavilyExtract** — использует Tavily API для извлечения контента
- **FireCrawl** — специализированный веб-скрапер
- **PyMuPDF** — для PDF документов
- **ArXivScraper** — для научных статей

**Процесс скрапинга:**
1. Определяет тип контента (HTML, PDF, etc.)
2. Выбирает подходящий scraper
3. Извлекает текст, изображения, метаданные
4. Очищает и структурирует контент

### 6. ContextManager (skills/context_manager.py)

**Управляет контекстом исследования.**

**Функции:**
- Семантический поиск релевантного контента по запросу
- Сжатие контекста для умещения в лимиты токенов
- Управление памятью между запросами
- Интеграция с vector stores

**Семантический поиск:**
- Использует embeddings для поиска релевантного контента
- Поддерживает различные embedding провайдеры (OpenAI, HuggingFace, Ollama, etc.)
- Фильтрует и ранжирует результаты по релевантности

### 7. SourceCurator (skills/curator.py)

**Фильтрует и ранжирует источники.**

**Функции:**
- Удаляет дубликаты
- Ранжирует источники по качеству и релевантности
- Фильтрует низкокачественный контент
- Ограничивает количество источников для оптимизации

### 8. DeepResearchSkill (skills/deep_research.py)

**Рекурсивное глубокое исследование.**

**Особенности:**
- Древовидная структура исследования с настраиваемой глубиной и шириной
- Параллельная обработка веток исследования
- Умное управление контекстом между ветками
- Извлечение ключевых инсайтов и генерация follow-up вопросов

**Процесс:**
1. Генерирует начальные исследовательские вопросы
2. Для каждого вопроса:
   - Проводит исследование
   - Извлекает ключевые инсайты
   - Генерирует follow-up вопросы
   - Рекурсивно углубляется в подтемы
3. Агрегирует результаты всех веток

**Параметры:**
- `breadth` — количество параллельных веток (по умолчанию 4)
- `depth` — глубина рекурсии (по умолчанию 2)
- `concurrency_limit` — лимит параллельных запросов (по умолчанию 2)

## Процесс работы (детальный)

### Этап 1: Инициализация

```python
researcher = GPTResearcher(
    query="why is Nvidia stock going up?",
    report_type="research_report",
    report_source="web",
    tone=Tone.Objective
)
```

**Что происходит:**
1. Загружается конфигурация (Config)
2. Инициализируются retrievers на основе RETRIEVER env variable
3. Настраивается Memory для embeddings
4. Создаются компоненты: ResearchConductor, ReportGenerator, ContextManager, etc.

### Этап 2: Выбор агента

Если агент не указан, система использует LLM для выбора подходящего агента:

```python
agent, role = await choose_agent(
    query=query,
    cfg=cfg,
    cost_callback=add_costs
)
```

**Примеры агентов:**
- Financial Analyst — для финансовых вопросов
- Technology Researcher — для технологических тем
- Academic Researcher — для академических исследований

### Этап 3: Планирование исследования

```python
sub_queries = await plan_research_outline(
    query=query,
    search_results=initial_search_results,
    agent_role_prompt=role,
    cfg=cfg
)
```

**Процесс:**
1. Выполняется начальный поиск по основному запросу
2. LLM анализирует результаты и генерирует под-вопросы
3. Под-вопросы разбивают тему на аспекты для глубокого исследования

**Пример под-вопросов для "why is Nvidia stock going up?":**
- "What are Nvidia's recent financial performance metrics?"
- "What new products or technologies has Nvidia launched?"
- "What is the current state of the AI chip market?"

### Этап 4: Параллельный сбор информации

Для каждого под-вопроса параллельно выполняется:

```python
context = await asyncio.gather(
    *[process_sub_query(sub_query) for sub_query in sub_queries]
)
```

**Для каждого под-вопроса:**

1. **Поиск URL** (`_search_relevant_source_urls()`):
   - Проходит по всем настроенным retrievers
   - Каждый retriever выполняет поиск
   - Собирает уникальные URL

2. **Скрапинг контента** (`_scrape_data_by_urls()`):
   - Определяет тип контента (HTML, PDF, etc.)
   - Выбирает подходящий scraper
   - Извлекает текст, изображения, метаданные
   - Очищает и структурирует контент

3. **Извлечение релевантного контекста** (`get_similar_content_by_query()`):
   - Использует embeddings для семантического поиска
   - Фильтрует контент по релевантности к под-вопросу
   - Сжимает контент для умещения в лимиты токенов

4. **MCP интеграция** (если настроена):
   - Выбирает оптимальные MCP инструменты для запроса
   - Выполняет поиск через MCP серверы
   - Комбинирует результаты с веб-поиском

### Этап 5: Курация источников

```python
if cfg.curate_sources:
    context = await source_curator.curate_sources(research_data)
```

**Процесс:**
- Удаление дубликатов
- Ранжирование по качеству и релевантности
- Фильтрация низкокачественного контента
- Ограничение количества источников

### Этап 6: Генерация отчета

```python
report = await researcher.write_report()
```

**Процесс:**
1. Формируется промпт с контекстом, ролью агента, типом отчета
2. LLM генерирует структурированный отчет
3. Добавляются цитаты к источникам
4. Форматируется в выбранный формат (markdown, PDF, DOCX)

**Структура отчета:**
- Введение
- Основные разделы (на основе под-вопросов)
- Заключение
- Список источников с цитатами

## Особенности реализации

### Параллелизм

Система активно использует `asyncio` для параллельной обработки:
- Параллельный поиск через разные retrievers
- Параллельная обработка под-вопросов
- Параллельный скрапинг URL
- Параллельная генерация разделов отчета

### Управление контекстом

- **Сжатие контекста**: автоматическое сжатие для умещения в лимиты токенов
- **Семантический поиск**: использование embeddings для поиска релевантного контента
- **Memory**: сохранение контекста между запросами
- **Vector Store**: интеграция с внешними vector stores для семантического поиска

### MCP интеграция

**Model Context Protocol (MCP)** позволяет подключать специализированные источники данных:

- **GitHub** — поиск в репозиториях
- **Базы данных** — подключение к БД
- **Custom APIs** — пользовательские API

**Стратегии MCP:**
- **fast**: запуск один раз для основного запроса (производительность)
- **deep**: запуск для каждого под-вопроса (тщательность)
- **disabled**: отключение MCP

### Поддержка различных источников

- **Web**: веб-поиск через различные поисковые системы
- **Local**: локальные документы (PDF, DOCX, TXT, CSV, Excel, PowerPoint, Word)
- **Hybrid**: комбинация веб и локальных источников
- **Azure**: документы из Azure Blob Storage
- **Vector Store**: семантический поиск в vector stores
- **LangChain Documents**: интеграция с LangChain документами

### Обработка ошибок и устойчивость

- Graceful degradation: если один retriever не работает, используются другие
- Retry логика для неудачных запросов
- Fallback на альтернативные LLM модели
- Логирование всех этапов процесса

## Конфигурация

### Переменные окружения

**Основные:**
- `OPENAI_API_KEY` — ключ OpenAI API
- `TAVILY_API_KEY` — ключ Tavily API
- `RETRIEVER` — список retrievers (например, "tavily,bing,mcp")

**LLM настройки:**
- `FAST_LLM` — быстрая модель для простых задач
- `SMART_LLM` — умная модель для сложных задач
- `STRATEGIC_LLM` — стратегическая модель для планирования

**Embeddings:**
- `EMBEDDING` — провайдер embeddings (openai, huggingface, ollama, etc.)

**MCP:**
- `MCP_STRATEGY` — стратегия MCP (fast/deep/disabled)

### Конфигурационные файлы

Система поддерживает JSON конфигурационные файлы для детальной настройки всех параметров.

## Производительность и оптимизация

### Оптимизации:

1. **Кеширование MCP результатов** — при стратегии "fast" результаты кешируются и переиспользуются
2. **Параллельная обработка** — использование asyncio для параллельного выполнения задач
3. **Сжатие контекста** — автоматическое сжатие для умещения в лимиты токенов
4. **Worker Pool** — пул воркеров для ограничения параллельных запросов
5. **Rate Limiting** — ограничение частоты запросов к API

### Метрики:

- **Время исследования**: зависит от количества под-вопросов и источников (обычно 2-5 минут)
- **Стоимость**: зависит от используемых LLM моделей (обычно $0.1-$0.5 за исследование)
- **Качество**: агрегация из 20+ источников для объективных выводов

## Сравнение с другими подходами

### Преимущества:

1. **Параллелизм**: параллельная обработка под-вопросов ускоряет исследование
2. **Множество источников**: агрегация из 20+ источников снижает риск ошибок
3. **Автоматизация**: полная автоматизация процесса исследования
4. **Гибкость**: поддержка различных источников и форматов
5. **Цитаты**: автоматическое добавление цитат к источникам

### Ограничения:

1. **Зависимость от LLM**: качество зависит от используемых LLM моделей
2. **Стоимость**: использование платных API может быть дорогим
3. **Время**: глубокое исследование занимает несколько минут
4. **Токены**: ограничения по длине контекста

GPT Researcher представляет собой мощную систему для автоматизированного исследования, которая:

- Использует подход "планировщик-исполнитель" для структурированного исследования
- Параллельно обрабатывает множество источников для объективности
- Поддерживает различные источники данных (веб, локальные документы, MCP)

Система особенно полезна для задач, требующих глубокого исследования с множеством источников и объективными выводами.
