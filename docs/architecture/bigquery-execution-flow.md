# Архитектура выполнения запросов BigQuery/Vertex AI

## Текущая архитектура (наша реализация)

### Как это работает сейчас:

```
Пользователь: "Покажи документы проекта X"
    ↓
1. Наш сервис (BigQueryAIService)
   - Вызывает Vertex AI API для генерации SQL
   - Vertex AI возвращает SQL запрос
    ↓
2. Наш сервис выполняет SQL
   - Использует BigQueryClient.ExecuteQuery()
   - Отправляет SQL в BigQuery
    ↓
3. BigQuery выполняет SQL
   - Читает данные из таблиц/Object Tables
   - Возвращает результаты
    ↓
4. Наш сервис обрабатывает результаты
   - Конвертирует BigQuery типы в JSON
   - Возвращает пользователю
```

### Кто что делает:

- **Vertex AI**: Генерирует SQL из естественного языка (наш код вызывает API)
- **Наш сервис**: Выполняет SQL в BigQuery (наш код)
- **BigQuery**: Выполняет SQL и возвращает данные (GCP сервис)

## Альтернативный подход: BigQuery встроенный NL2SQL

### Существует ли встроенная интеграция?

**Короткий ответ:** Нет, BigQuery не имеет встроенной функции для выполнения запросов на естественном языке напрямую.

**Что есть:**
- BigQuery ML может вызывать модели Vertex AI **внутри SQL запросов** (ML.GENERATE_TEXT)
- Но это не то же самое, что NL2SQL - это для анализа контента, а не для генерации SQL

### Пример BigQuery ML с Vertex AI:

```sql
-- Это НЕ генерация SQL, а анализ контента через ML внутри SQL
SELECT 
  id,
  ML.GENERATE_TEXT(
    MODEL `prevalent-horizon-test.horizon_documents.gemini_model`,
    extractedText,
    STRUCT('Summarize this document' AS prompt)
  ) AS summary
FROM documents_metadata
```

Это работает **внутри SQL**, но сам SQL все равно нужно писать вручную или генерировать отдельно.

## Почему мы делаем так (текущая архитектура)

### Преимущества нашего подхода:

1. **Полный контроль** над генерацией SQL
   - Можем улучшать промпты
   - Можем добавлять валидацию
   - Можем исправлять ошибки автоматически

2. **Гибкость**
   - Можем использовать любую модель Vertex AI
   - Можем настраивать температуру, токены и т.д.
   - Можем добавлять бизнес-логику

3. **Прозрачность**
   - Возвращаем сгенерированный SQL пользователю
   - Можем логировать все запросы
   - Легко отлаживать

4. **Автоматическое исправление ошибок**
   - При ошибке можем регенерировать SQL
   - Используем сообщение об ошибке для улучшения

### Недостатки:

1. **Два вызова API** вместо одного
   - Сначала Vertex AI для генерации SQL
   - Потом BigQuery для выполнения

2. **Задержка**
   - Генерация SQL занимает время
   - Затем выполнение SQL

## Можно ли сделать иначе?

### Вариант 1: BigQuery + Vertex AI напрямую (не поддерживается)

**Проблема:** BigQuery не имеет встроенной функции для NL2SQL. Нет такой функции как:
```sql
-- Этого НЕ существует
SELECT * FROM NATURAL_LANGUAGE_QUERY('Покажи документы проекта X')
```

### Вариант 2: Использовать BigQuery ML для всего (сложно)

Можно было бы попробовать использовать BigQuery ML для генерации SQL, но это потребовало бы:
- Обучения модели специально для нашей схемы
- Сложной настройки
- Меньшей гибкости

### Вариант 3: Текущий подход (наш выбор) ✅

**Преимущества:**
- Работает "из коробки"
- Гибкий и настраиваемый
- Автоматическое исправление ошибок
- Прозрачность для пользователя

## Итог

**Текущая архитектура:**
- Vertex AI генерирует SQL (наш код вызывает API)
- Мы выполняем SQL в BigQuery (наш код)
- BigQuery возвращает данные (GCP сервис)

**Альтернативы:**
- BigQuery не имеет встроенного NL2SQL
- BigQuery ML работает внутри SQL, но не генерирует SQL
- Наш подход оптимален для гибкости и контроля

## Будущие возможности

Если Google добавит встроенную поддержку NL2SQL в BigQuery, мы сможем переключиться на неё, но пока такого функционала нет.
