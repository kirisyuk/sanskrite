# Технические решения и обоснования

## Обзор

Данный документ описывает ключевые технические решения, принятые при проектировании системы мониторинга горизонта, и обоснования этих решений.

## 1. Использование Firestore вместо графовой БД

### Решение

Использовать Firestore с индексами для хранения графа зависимостей на первом этапе, отложив миграцию на специализированную графовую БД.

### Обоснование

**Преимущества**:
- Простота интеграции с общей инфраструктурой ядра
- Единая система хранения данных (меньше сложности)
- Достаточная производительность для начального этапа
- Низкие операционные затраты
- Возможность миграции в будущем без изменения API

**Недостатки**:
- Сложные графовые запросы (например, поиск путей) требуют дополнительной логики
- Масштабирование для очень больших графов может быть проблематичным
- Отсутствие нативных графовых операций

**Альтернативы**:
- Neo4j: Мощная графовая БД, но требует отдельной инфраструктуры
- Amazon Neptune: Управляемый сервис, но дополнительные затраты
- ArangoDB: Мультимодельная БД, но сложнее в интеграции

**Когда пересмотреть**:
- При необходимости сложных графовых запросов
- При масштабировании до миллионов узлов
- При требованиях к производительности графовых операций

## 2. Архитектура "Зал Суда" для верификации данных

### Решение

Использовать состязательное взаимодействие трех LLM-агентов (Scout, Critic, Resolver) для верификации данных.

### Обоснование

**Преимущества**:
- Высокое качество данных через множественную проверку
- Минимизация "галлюцинаций" LLM
- Прозрачность процесса принятия решений
- Аудит через Chain of Thought

**Недостатки**:
- Увеличение стоимости (3 LLM вызова вместо 1)
- Увеличение времени выполнения
- Сложность настройки промптов

**Альтернативы**:
- Один LLM с детальным промптом: Быстрее и дешевле, но менее надежно
- Человеческая проверка: Высокое качество, но не масштабируется
- Правила и эвристики: Быстро, но недостаточно гибко

**Оптимизации**:
- Использование более дешевых моделей для Critic где возможно
- Кэширование результатов валидации
- Параллельное выполнение Scout и Critic

## 3. Constrained Decoding для генерации JSON

### Решение

Использовать constrained decoding для принудительной генерации валидного JSON без дополнительных текстовых пояснений.

### Обоснование

**Преимущества**:
- Гарантированно валидный JSON
- Отсутствие необходимости парсинга и очистки ответов
- Меньше ошибок форматирования
- Более предсказуемое поведение

**Недостатки**:
- Не все провайдеры поддерживают constrained decoding
- Может ограничивать творческие возможности LLM
- Требует точных схем данных

**Реализация**:
- Использование JSON mode в OpenAI API
- Использование structured outputs в Anthropic API
- Использование response_schema в Vertex AI

## 4. Wave Damping для контроля распространения изменений

### Решение

Использовать алгоритм затухания волны для предотвращения экспоненциального роста нагрузки при распространении изменений.

### Обоснование

**Преимущества**:
- Предотвращение "эффекта домино"
- Контроль вычислительной нагрузки
- Масштабируемость для больших графов
- Предсказуемое поведение системы

**Недостатки**:
- Возможна потеря незначительных изменений
- Требует настройки коэффициентов затухания
- Сложность отладки распространения

**Альтернативы**:
- Полное распространение: Проще, но не масштабируется
- Пороговое распространение: Проще, но менее гибко
- Машинное обучение: Более умно, но сложнее

**Параметры**:
- `damping_factor`: 0.8-0.9 (настраивается)
- `max_depth`: 5-10 уровней (настраивается)
- `min_influence`: 0.01 (критический уровень)

## 5. Lazy Evaluation (Hot Path / Cold Path)

### Решение

Разделить пересчет Lens на Hot Path (немедленный) и Cold Path (отложенный) для оптимизации производительности.

### Обоснование

**Преимущества**:
- Оптимизация использования ресурсов
- Быстрый отклик для активных пользователей
- Снижение нагрузки на систему
- Лучший UX для активных Lens

**Недостатки**:
- Сложность определения Hot Path
- Возможна задержка обновлений для Cold Path
- Требует управления очередями

**Критерии Hot Path**:
- Последний доступ < 5 минут
- Приоритет = "critical"
- Активные подписчики > 0

**Критерии Cold Path**:
- Последний доступ > 1 часа
- Приоритет = "low"
- Нет активных подписчиков

## 6. Reference Counting для управления жизненным циклом

### Решение

Использовать счетчик активных подписчиков (activeSubscribers) для управления жизненным циклом HorizonFragment.

### Обоснование

**Преимущества**:
- Простота реализации
- Автоматическое управление ресурсами
- Прозрачность состояния узлов
- Эффективное использование ресурсов

**Недостатки**:
- Требует аккуратного управления счетчиками
- Возможны утечки при ошибках
- Необходимость периодической проверки целостности

**Альтернативы**:
- TTL (Time To Live): Проще, но менее гибко
- LRU кэш: Сложнее, но более умно
- Политики на основе использования: Сложнее, но более точно

**Реализация**:
- Атомарные операции для инкремента/декремента
- Транзакции для обеспечения консистентности
- Периодическая проверка целостности счетчиков

## 7. Неизменяемость Frame

### Решение

Frame документы являются неизменяемыми (immutable) - любое обновление создает новый Frame.

### Обоснование

**Преимущества**:
- Полная история изменений
- Аудит и прослеживаемость
- Отсутствие проблем с конкурентным доступом
- Простота отката изменений

**Недостатки**:
- Увеличение объема хранилища
- Необходимость управления версиями
- Сложность запросов по истории

**Альтернативы**:
- Мутабельные документы: Меньше хранилища, но сложнее аудит
- Версионирование полей: Компромисс, но сложнее

**Оптимизации**:
- Архивация старых Frame в холодное хранилище
- Сжатие данных для старых версий
- Индексы только для последних версий

## 8. Использование существующей AI системы

### Решение

Использовать существующую AI систему (`internal/ai`) вместо создания новой.

### Обоснование

**Преимущества**:
- Переиспользование существующего кода
- Единая точка интеграции с LLM провайдерами
- Консистентность с остальной системой
- Меньше дублирования кода

**Недостатки**:
- Зависимость от существующей архитектуры
- Возможные ограничения существующего API
- Необходимость расширения при необходимости

**Расширения**:
- Добавление поддержки constrained decoding
- Добавление метрик использования для Scout агентов
- Оптимизация для batch обработки

## 9. Cloud Functions для Watchdog

### Решение

Использовать Cloud Functions с Cloud Scheduler для фоновых задач Watchdog.

### Обоснование

**Преимущества**:
- Автоматическое масштабирование
- Низкие операционные затраты
- Простота развертывания
- Интеграция с GCP экосистемой

**Недостатки**:
- Ограничения времени выполнения (для Cloud Functions)
- Холодный старт может быть медленным
- Меньше контроля над окружением

**Альтернативы**:
- Cloud Run Jobs: Больше контроля, но сложнее
- Внутренний сервис: Больше контроля, но больше операционных затрат
- Kubernetes CronJobs: Максимальный контроль, но сложнее

**Выбор**:
- Cloud Functions для простых периодических задач
- Cloud Run Jobs для сложных задач с длительным выполнением

## 10. Мультитенантность через TenantID

### Решение

Использовать TenantID во всех моделях для изоляции данных между тенантами.

### Обоснование

**Преимущества**:
- Простота реализации
- Консистентность с существующей системой
- Эффективная изоляция данных
- Легкая миграция на физическую изоляцию при необходимости

**Недостатки**:
- Логическая изоляция (не физическая)
- Необходимость проверки TenantID во всех запросах
- Возможные ошибки при неправильной проверке

**Безопасность**:
- Проверка TenantID на уровне репозиториев
- Middleware для автоматической проверки
- Аудит доступа к данным
