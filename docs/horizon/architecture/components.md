# Компоненты системы мониторинга горизонта

## Обзор

Система состоит из четырех основных компонентов: Scout Engine, Propagation Engine, Lens Subsystem и Watchdog Service. Каждый компонент отвечает за определенную область функциональности и интегрируется с существующей инфраструктурой Sanskrite.

## Scout Engine

### Назначение

Scout Engine отвечает за автоматический сбор и верификацию данных из внешних источников с использованием архитектуры "Зал Суда" (The Courtroom).

### Архитектура "Зал Суда"

Процесс верификации данных строится на состязательном взаимодействии нескольких LLM-агентов:

#### Scout Agent (Искатель)

**Роль**: Поиск и первичное извлечение информации

**Задачи**:
- Поиск релевантных источников (API, веб-страницы, документы)
- Извлечение фактов в строго типизированный JSON-формат
- Соответствие заданной Pydantic-схеме

**Модели**: GPT-5.2, Claude 4.5, Gemini 3 Pro

**Выходные данные**: JSON-объект с извлеченными метриками состояния

#### Critic Agent (Критик)

**Роль**: Проверка данных на соответствие источникам

**Задачи**:
- Получение исходного текста и сгенерированного JSON от Scout
- Поиск несоответствий между данными и источниками
- Выявление логических противоречий
- Проверка фактов, не подтвержденных источником

**Модели**: Claude 4.5 Opus

**Выходные данные**: Список найденных несоответствий и аргументы

#### Resolver Agent (Резольвер)

**Роль**: Финальное решение о статусе данных

**Задачи**:
- Анализ данных Scout и аргументов Critic
- Вынесение финального вердикта: Verified, Rejected, Low_Confidence
- Генерация цепочки рассуждений (Chain of Thought) для аудита

**Модели**: GPT-5.2, Claude 4.5

**Выходные данные**: Вердикт и обоснование решения

### Требования

#### Жесткие схемы данных

- Все извлеченные данные должны соответствовать предопределенным Pydantic-схемам
- Любое отклонение приводит к автоматическому повтору запроса с уточнением
- Использование constrained decoding для генерации только валидного JSON

#### Прозрачность

- Каждый Frame содержит ссылки на исходные источники
- Опциональная цепочка рассуждений Resolver для аудита
- Полная прослеживаемость от источника до факта

### Интеграция

**Использует**:
- `internal/ai` — для LLM вызовов
- `internal/agents` — для оркестрации задач
- `internal/crawler` — для сбора данных из источников

**Создает**:
- Frame документы в Firestore коллекции `frames`
- HorizonFragment обновления в коллекции `horizon_fragments`

### Workflow состояний

```
PENDING → PLANNING → EXECUTION → EXTRACTION → VALIDATION → RESOLUTION → VERIFIED
```

Подробнее см. [Scout Workflow](../workflows/scout-workflow.md)

## Propagation Engine

### Назначение

Propagation Engine отвечает за распространение изменений в графе зависимостей с контролем вычислительной нагрузки и предотвращением экспоненциального роста.

### Алгоритмы

#### Delta Threshold (Порог значимости)

**Принцип**: Система реагирует не на любое изменение, а только на превышающее порог

**Реализация**:
- Адаптивные пороги на основе исторической волатильности метрик
- Разные пороги для разных типов метрик
- Фильтрация шума и незначительных изменений

**Пример**:
```go
if abs(newValue - oldValue) < threshold {
    // Изменение игнорируется
    return
}
```

#### Wave Damping (Затухание волны)

**Принцип**: Влияние события уменьшается по мере распространения по графу

**Реализация**:
- Вес ребра (DependencyEdge) определяет коэффициент затухания
- Влияние умножается на `amplification * (1 - damping_factor)`
- Если влияние падает ниже критического уровня, волна останавливается

**Формула**:
```
influence = initial_influence * (amplification ^ depth) * damping_factor
```

#### Lazy Evaluation (Ленивые вычисления)

**Принцип**: Пересчет графа выполняется по приоритету

**Hot Path**:
- Немедленный пересчет для активно используемых Lens
- Помеченные как критические Lens
- Время отклика: ≤ 5 секунд

**Cold Path**:
- Отложенный пересчет для неактивных Lens
- По запросу пользователя или по расписанию
- Время отклика: ≤ 1 минуты

#### Topological Optimization

**Принцип**: Обработка изменений на критическом пути в первую очередь

**Реализация**:
- Определение критического пути для каждой Lens
- Приоритетная обработка узлов с наибольшим совокупным влиянием
- Оптимизация порядка пересчета

### Интеграция

**Использует**:
- `internal/repo` — для чтения DependencyEdge и HorizonFragment
- `internal/realtime` — для публикации обновлений Lens

**Создает**:
- События обновления Lens через Pub/Sub
- WebSocket уведомления для фронтенда

### События

- `propagation.started` — начало распространения изменений
- `propagation.node_updated` — обновление узла в графе
- `propagation.lens_recalculated` — пересчет Lens
- `propagation.completed` — завершение распространения

## Lens Subsystem

### Назначение

Lens Subsystem управляет пользовательскими конфигурациями мониторинга и анализа графа знаний.

### Функции

#### Управление Lens

- Создание, обновление, удаление Lens
- Валидация scope (canonical_path узлов)
- Управление статусом (ACTIVE, ARCHIVED)

#### Подписка на HorizonFragment

- Автоматическая подписка при добавлении узла в scope
- Инкремент счетчика `activeSubscribers` у HorizonFragment
- Управление жизненным циклом узлов

#### Конфигурация визуализации

- Настройки глубины графа (depth)
- Тип представления (graph, table, timeline)
- Фильтры и сортировка

#### Конфигурация оповещений

- Пороги для метрик (thresholds)
- Каналы уведомлений (email, websocket)
- Правила генерации алертов

### Интеграция

**Использует**:
- `internal/repo` — для работы с Lens и HorizonFragment
- `internal/realtime` — для обновлений в реальном времени
- `internal/projects` — для связи с Project

**Создает**:
- Lens документы в Firestore коллекции `lenses`
- Обновления HorizonFragment (activeSubscribers)

### API

- `POST /api/horizon/lenses` — создание Lens
- `GET /api/horizon/lenses/{id}` — получение Lens
- `PUT /api/horizon/lenses/{id}` — обновление Lens
- `DELETE /api/horizon/lenses/{id}` — удаление Lens
- `POST /api/horizon/lenses/{id}/recalculate` — принудительный пересчет

## Watchdog Service

### Назначение

Watchdog Service осуществляет фоновый мониторинг внешних источников для активных HorizonFragment и инициирует обновления при обнаружении изменений.

### Функции

#### Периодический мониторинг

- Планирование проверок на основе `scanInterval`
- Проверка источников из `sourceList`
- Обнаружение изменений контента через сравнение хешей

#### Обнаружение изменений

- Вычисление хеша контента источника (SHA256)
- Сравнение с предыдущим хешем
- Если изменение превышает `triggerThreshold` → создание ScoutRequest

#### Управление жизненным циклом

- Автоматический запуск для узлов со статусом ACTIVE
- Автоматическая остановка для узлов со статусом DORMANT
- Управление статусом (RUNNING, PAUSED)

### Интеграция

**Использует**:
- `internal/crawler` — для получения контента источников
- `internal/horizon/scout` — для создания ScoutRequest
- `internal/repo` — для работы с WatchdogConfig

**Создает**:
- ScoutRequest для обновления HorizonFragment
- События обнаружения изменений

### Реализация

**Варианты**:
1. **Cloud Functions** — для периодических задач (Cloud Scheduler)
2. **Cloud Run Jobs** — для более сложной логики
3. **Внутренний сервис** — для интеграции в моноядро

**Рекомендация**: Cloud Functions с Cloud Scheduler для простоты и масштабируемости

### Конфигурация

```json
{
  "scanInterval": "PT1H",
  "sourceList": [
    "https://www.reuters.com/...",
    "https://api.example.com/..."
  ],
  "triggerThreshold": 0.1
}
```

## Взаимодействие компонентов

### Сценарий: Обновление HorizonFragment

1. **Watchdog** обнаруживает изменение в источнике
2. **Watchdog** создает ScoutRequest
3. **Scout Engine** выполняет сбор и верификацию данных
4. **Scout Engine** создает новый Frame
5. **Scout Engine** обновляет HorizonFragment
6. **Propagation Engine** проверяет порог значимости (Delta Threshold)
7. Если превышен → **Propagation Engine** запускает волну распространения
8. **Propagation Engine** пересчитывает зависимые Lens
9. **Lens Subsystem** получает обновления через Realtime
10. **Frontend** получает уведомления через WebSocket

### Сценарий: Создание нового Lens

1. Пользователь создает Lens через API
2. **Lens Subsystem** валидирует scope
3. Для каждого узла в scope:
   - Проверка существования HorizonFragment
   - Если не существует → создание ScoutingJob (Pioneer модель)
   - Если существует → подписка на узел (инкремент activeSubscribers)
4. **Lens Subsystem** создает Lens документ
5. Если узел был DORMANT → переход в ACTIVE, запуск Watchdog
6. **Propagation Engine** выполняет начальный пересчет Lens
