# Interface Principles

## Назначение

Этот документ фиксирует не устройство конкретного продукта, а **общие принципы построения UX и интерфейсной системы** для строгих аналитических инструментов.

Он нужен для того, чтобы переносить не внешний вид отдельных экранов, а:

- способ входа пользователя в задачу;
- организацию пространства;
- правила визуальной тишины;
- принципы навигации;
- поведение сложных рабочих поверхностей;
- требования к интерфейсу, если система уже умеет искать, собирать или генерировать релевантную информацию.

## 1. Основная доктрина

### 1.1. Главный принцип

Интерфейс должен делать две вещи:

- **минимизировать отвлечение от задачи**;
- **минимизировать усилие входа пользователя**.

Это важнее стилистики, декоративности и даже полноты интерфейса на первом экране.

Если упростить до одного правила:

- если пользователь уже может работать с релевантной информацией, ему надо сразу показать рабочую поверхность;
- если релевантной информации ещё нет, ему надо дать самый короткий путь её получить.

### 1.2. Интерфейс должен подчиняться задаче, а не демонстрировать систему

Пользователь приходит не смотреть на устройство продукта. Он приходит:

- найти;
- открыть;
- понять;
- собрать;
- проверить;
- спросить;
- исследовать;
- принять решение.

Поэтому интерфейс не должен в первую очередь объяснять:

- внутреннюю архитектуру;
- набор сущностей;
- все режимы работы;
- полный набор возможностей.

Он должен сначала вести в задачу.

### 1.3. Низкий порог входа важнее демонстрации мощности

Даже если система сложная, вход должен быть простым.

Пользователь должен иметь возможность начать с формулировок уровня:

- “найди ...”;
- “открой ...”;
- “покажи ...”;
- “что происходит с ...”;
- “собери мне ...”;
- “исследуй ...”.

Сложность должна раскрываться позже, по мере движения в задаче.

## 2. Центральная логика экрана

### 2.1. Центр экрана принадлежит только задаче

Центральная область интерфейса должна быть зарезервирована под одно из двух состояний:

- **рабочая поверхность**, если уже есть релевантная информация;
- **task-entry surface**, если релевантной информации ещё нет.

Иных главных состояний у центра быть не должно.

### 2.2. Если информация уже есть, в центре должен быть canvas

Если система уже может показать пользователю содержательное рабочее представление, в центре должна быть именно рабочая модель:

- canvas;
- graph;
- карта;
- таблица;
- аналитический слой;
- другой основной рабочий вид.

Центр не должен в этом случае быть занят:

- промо-блоками;
- длинными объяснениями;
- вторичной навигацией;
- случайными карточками;
- декоративными панелями.

### 2.3. Если информации ещё нет, в центре должен быть command palette или основной task input

Если рабочей модели ещё нет, центр должен занимать интерфейс постановки задачи:

- command palette;
- поисковый вход;
- основной запросный input;
- минимальная форма task entry.

Это состояние должно быть максимально коротким по пути к действию:

- сформулировать;
- выбрать;
- подтвердить;
- получить рабочую модель.

### 2.4. Центр не должен быть “зоной ожидания”

Пустой центр не должен ощущаться как отсутствие сценария.

Если информации нет, пользователь должен видеть:

- что можно сделать;
- как это сделать;
- минимальный способ начать.

Пустота должна ощущаться как приглашение к постановке задачи, а не как незаполненный макет.

## 3. Вход в задачу

### 3.1. Если задачу можно описать словами, пользователь не должен собирать её руками

Если система умеет:

- интерпретировать текст;
- искать по названиям;
- распознавать сущности;
- находить релевантный контекст;
- достраивать намерение пользователя,

то интерфейс должен использовать это как основной вход.

Правильный порядок:

- сначала пользователь говорит, что ему нужно;
- потом система уточняет только действительно недостающее;
- потом открывается рабочая поверхность.

Неправильный порядок:

- сначала пользователь вручную собирает режим;
- потом выбирает тип;
- потом фильтр;
- потом представление;
- потом глубину;
- потом параметры;
- и только потом формулирует задачу.

### 3.2. Search-first и language-first предпочтительнее конфигурации-first

Если действие можно начать через:

- поиск;
- слова;
- естественный запрос;
- выбор найденного объекта,

это должно быть предпочтительным входом.

Ручная конфигурация уместна только:

- как уточнение;
- как профессиональная надстройка;
- как advanced mode;
- как вторичный инструмент после входа в задачу.

### 3.3. Минимум обязательных решений до первого полезного результата

До первого содержательного результата пользователь не должен принимать много решений.

Идеально, если до первого полезного состояния нужно:

- ввести запрос;
- выбрать найденное;
- подтвердить действие.

Чем больше обязательных шагов до первого результата, тем выше трение и тем хуже интерфейс.

## 4. Command Palette

### 4.1. Command palette нужна для сокращения трения

Command palette не является декоративным паттерном. Её задача:

- сократить число кликов;
- сократить число переключений контекста;
- сократить число обязательных решений;
- свести сложное действие к короткому входу.

### 4.2. Command palette не должна становиться отдельным приложением

Palette не должна превращаться в сложный интерфейс внутри интерфейса.

Её роль ограничена:

- принять запрос;
- показать результаты;
- дать выбрать действие;
- запустить переход к рабочей поверхности.

Если palette начинает содержать слишком много:

- самостоятельных режимов;
- разнотипных карточек;
- сложных вложенных блоков;
- длинных форм,

она теряет смысл.

### 4.3. В palette должен доминировать один input

Внутри palette главным элементом должен быть ввод.

Всё остальное подчинено ему:

- список результатов;
- уточняющие подсказки;
- быстрые действия;
- минимальная вторичная информация.

### 4.4. Внутри palette должно быть минимум визуальных дистракторов

Palette должна быть визуально тихой.

Недопустимы:

- яркие плашки без необходимости;
- несколько равносильных акцентов;
- тяжёлые декоративные блоки;
- визуально громкие карточки;
- лишние бейджи;
- обилие вторичного текста.

Правильная palette:

- спокойная;
- компактная;
- текстоцентричная;
- быстрая для сканирования;
- подчинённая задаче.

### 4.5. Palette должна быть keyboard-first

Если используется command palette, у неё должны быть очевидны:

- мгновенный фокус на ввод;
- стрелочная навигация;
- Enter как главный action;
- Escape как главный выход;
- предсказуемое поведение выбора.

## 5. Пространственная организация интерфейса

### 5.1. Пространство делится по роли

Хороший аналитический интерфейс строится не по принципу “куда поместить компонент”, а по принципу “какую роль играет область”.

Базовое деление:

- слева: навигация и выбор контекста;
- сверху: глобальный системный слой;
- снизу: тихий сервисный слой;
- в центре: основная задача;
- справа: контекстная инспекция или объяснение.

### 5.2. Навигация всегда слева

Левая колонка отвечает за:

- выбор рабочего контекста;
- переключение между рабочими объектами;
- доступ к спискам и структурам;
- переход между контейнерами работы.

Она не должна забирать на себя основную аналитическую работу.

### 5.3. Top bar является системным слоем

Верхняя панель нужна для глобального, а не для локальной задачи.

Там допустимы:

- идентичность продукта;
- глобальная навигация;
- аккаунт;
- язык;
- тема;
- глобальные системные действия.

Там не должны жить детали конкретного рабочего объекта, если они относятся только к центральной задаче.

### 5.4. Bottom bar является тихим сервисным слоем

Нижняя панель должна быть компактной и ненавязчивой.

Её задача:

- системный статус;
- юридический контур;
- малошумные вторичные сигналы.

Она не должна конкурировать с top bar и не должна быть второй навигационной зоной.

### 5.5. Правая панель всегда вторична и контекстна

Правая панель существует не сама по себе, а только как расширение текущего выбора.

Её роль:

- объяснить выбранное;
- показать детали;
- открыть контекстную инспекцию;
- дать вторичный drill-down.

Если выбранного контекста нет, правая панель не должна создавать ощущение пустой зарезервированной территории.

## 6. Layout-принципы

### 6.1. Один главный layout важнее множества несвязанных экранов

Даже если интерфейс содержит разные режимы, они должны ощущаться как состояния одной рабочей станции, а не как набор разных продуктов.

Пользователь должен сохранять:

- ориентацию в пространстве;
- понимание, где находится навигация;
- понимание, где находится рабочая зона;
- понимание, где искать детали и действия.

### 6.2. Viewport-first лучше document-first

Для аналитических инструментов главный экран должен проектироваться как рабочее пространство в рамках viewport, а не как длинный документ.

Это означает:

- локальные скроллы внутри областей;
- стабильная высота центральной зоны;
- предсказуемое поведение панелей;
- отсутствие “расползания” интерфейса вниз.

### 6.3. Панели не должны бороться за главный приоритет

На экране всегда должна быть одна основная область внимания.

Если всё выглядит одинаково важным:

- layout не работает;
- пользователь не понимает, с чего начать;
- интерфейс начинает отвлекать от задачи.

### 6.4. Сложность должна раскрываться слоями

Хороший layout показывает:

- сначала главное;
- потом контекст;
- потом детали;
- потом дополнительные инструменты.

Не наоборот.

## 7. Визуальная тишина

### 7.1. Строгий интерфейс лучше развлекательного

Для task-oriented аналитических систем характер интерфейса должен быть:

- спокойным;
- собранным;
- плотным;
- функциональным.

Он не должен быть:

- игривым;
- шумным;
- рекламным;
- “дружелюбно-перегретым”.

### 7.2. Визуальный шум является UX-дефектом

Шумом считаются:

- лишние акценты;
- конкурирующие CTA;
- большое количество случайных цветов;
- карточки без смысловой функции;
- постоянные украшения;
- тяжёлые визуальные эффекты без пользы.

Чем выше требования к концентрации, тем строже нужно вычищать шум.

### 7.3. Цвет должен быть функциональным

Цвет нужен не для украшения, а для различения:

- статуса;
- важности;
- типа действия;
- уровня риска;
- уровня фокуса.

Если цвет не несёт функции, его лучше убрать.

### 7.4. Поверхности должны иметь ясную иерархию

Пользователь должен без усилия различать:

- фон;
- основную рабочую поверхность;
- вторичные панели;
- overlay;
- modal;
- selected state;
- inactive state.

Различение достигается через:

- тон;
- контраст;
- прозрачность;
- border;
- тень;
- плотность.

## 8. Типографика и иконография

### 8.1. Типографика должна быть служебной, а не самовыражающейся

Шрифт и иерархия текста должны помогать:

- быстро сканировать интерфейс;
- удерживать плотность информации;
- отличать главное от вторичного;
- не перегружать экран.

### 8.2. Заголовки не должны кричать

В строгом интерфейсе заголовок ориентирует, а не пытается впечатлить.

Даже крупная типографика должна выглядеть как часть системы, а не как отдельный промо-слой.

### 8.3. Иконки должны быть монохромными и подчинёнными

Иконка нужна для ускорения считывания действия, а не как самостоятельная визуальная сущность.

Правильные свойства:

- монохромность;
- единая геометрия;
- единый stroke language;
- цвет через `currentColor` или токены;
- вторичность по отношению к смыслу.

### 8.4. Иконка не должна заменять текст там, где нужна точность

Если действие требует точного понимания, иконка должна сопровождаться подписью.

Чисто иконографические кнопки уместны только там, где действие уже стало узнаваемым паттерном.

## 9. Поведение состояний

### 9.1. Empty state должен вести к действию

Пустое состояние должно не описывать продукт слишком долго, а помогать начать.

Оно должно:

- кратко объяснить, что можно сделать;
- предложить один главный путь входа;
- не создавать визуального шума.

### 9.2. Loading state должен быть локальным и аккуратным

Загрузка не должна без необходимости захватывать весь интерфейс.

Правильная загрузка:

- локальна;
- спокойна;
- не драматизирует процесс;
- показывает, что идёт работа.

### 9.3. Долгий процесс должен иметь собственный UX

Если система выполняет длительную, ценообразующую или интеллектуально значимую работу, нельзя скрывать её за абстрактным спиннером.

Нужно показывать:

- ход процесса;
- этап;
- прогресс;
- события;
- состояние ошибок.

### 9.4. Ошибка должна быть контекстной

Ошибка должна появляться рядом с тем местом, где пользователь может понять её смысл и принять решение.

Не каждая локальная ошибка должна ломать всё приложение.

## 10. Motion

### 10.1. Анимация должна подтверждать состояние

Анимация допустима только если она помогает понять:

- что появилось;
- что изменилось;
- что загружается;
- что перешло в другое состояние.

### 10.2. Motion не должен мешать концентрации

Если анимация:

- отвлекает;
- раздражает;
- удлиняет переход без пользы;
- мешает чтению данных,

она ухудшает UX.

### 10.3. У сложных поверхностей должен быть режим деградации

Если интерфейс работает с тяжёлыми моделями, он должен уметь упрощаться:

- меньше эффектов;
- меньше тяжёлых overlay;
- меньше дорогих подсветок;
- больше производительности.

Производительность является частью UX, а не отдельной технической темой.

## 11. Адаптивность

### 11.1. Адаптация должна сохранять логику интерфейса

На меньших экранах можно менять:

- плотность;
- способ открытия панелей;
- объём одновременно видимых контролов.

Но нельзя ломать саму пространственную логику:

- навигация остаётся навигацией;
- рабочая поверхность остаётся рабочей поверхностью;
- inspector остаётся inspector.

### 11.2. Mobile-упрощение не должно превращаться в другой продукт

Если на desktop интерфейс решает задачу одним способом, mobile-версия должна упрощать подачу, а не перепридумывать всю механику.

## 12. Технические требования к хорошему UX

### 12.1. Интерфейс должен быть разделён по ответственности

Нельзя смешивать в одном месте:

- рендер;
- transport;
- нормализацию данных;
- глобальное состояние;
- доменную логику;
- эффекты подписки.

Хороший UX на сложной системе возможен только тогда, когда интерфейс архитектурно разделён.

### 12.2. Состояние должно поддерживать continuity, а не дублировать backend

Локально есть смысл хранить только то, что уменьшает трение:

- выбранный контекст;
- предпочтения представления;
- небольшие пользовательские настройки;
- continuity текущей сессии.

Нельзя превращать локальное состояние в вторую базу данных продукта.

### 12.3. Транспорт и realtime не должны протекать в компоненты

Компоненты должны работать с понятными интерфейсами, а не с raw transport-логикой.

Это нужно не только для чистоты кода, но и для стабильности UX:

- меньше race conditions;
- меньше случайных пересборок;
- понятнее error handling;
- легче держать интерфейс предсказуемым.

### 12.4. Интерфейс должен выдерживать асинхронность

Если система работает не мгновенно, UX должен быть рассчитан на:

- частичную готовность данных;
- обновления в фоне;
- приход релевантной информации после действия;
- смену локальных и удалённых состояний без визуального хаоса.

## 13. Краткий чеклист

- Главный принцип: минимум отвлечения от задачи и низкий порог входа.
- В центре либо рабочий canvas, либо command palette / task input.
- Если задачу можно описать словами, пользователь не должен собирать её руками.
- Navigation слева, top bar сверху, bottom bar снизу, правая зона под инспекцию и детали.
- Центр не тратится на вторичную навигацию и декоративные блоки.
- Command palette уменьшает трение и остаётся визуально тихой.
- Search-first и language-first лучше configuration-first.
- Layout сохраняет одну главную область внимания.
